# RIS-09: Comprehension Gate

**Target**: Puffin 4.0
**Dependencies**: none (benefits from RIS-05 evaluator when both exist)
**Delivery**: core change (`claude-service.js`, migration 013) + `comprehension-gate-plugin`
**Estimated effort**: 2 sprints

---

## 1. Motivation

The paper's Section 2.4 and Section 12.6 name the open question that Anthropic itself does not treat as a first-class design value: **long-term human capability preservation**. The empirical evidence the paper cites is stark — Shen and Tamkin find developers score 17% lower on comprehension tests in AI-assisted conditions; He et al. report +40.7% code complexity from Cursor adoption; Liu et al. document that roughly a quarter of AI-introduced issues persist in the latest revision; Kosmyna et al. find weakened neural connectivity that persists after AI is removed; Rak documents a 25% decline in entry-level tech hiring. The paper is unusually direct: "Future systems could treat that sustainability gap as a first-class design problem, not a downstream evaluation metric." Puffin — an artisanal, personal-developer-oriented harness — is the correct venue to take this seriously, and JJ's public thesis on artisanal software aligns with treating comprehension as a measurable outcome. This spec introduces a **comprehension gate** that fires at high-leverage moments and requires the developer to demonstrate understanding before accepting the change. It is deliberately opinionated: concrete triggers, concrete questions, concrete thresholds. Users can skip any gate (never blocking); skip rate is itself a metric. Integration point: the stream-json event flow in `claude-service.js` plus a new review-events table.

## 2. User-facing behavior

- When Claude completes a turn, Puffin evaluates the change against trigger conditions. A gate fires when any of:
  - ≥3 files modified in a single turn, OR
  - any single file with ≥100 lines added/removed, OR
  - any file matching `**/migrations/**` or `**/schema/**` patterns, OR
  - any new file under `src/main/` or `src/renderer/` (core-affecting).
- A gate opens a modal that blocks the "accept" state transition until dismissed. Modal contents:
  - **Diff summary**: files + line counts + a collapsed per-file diff view.
  - **Three multiple-choice questions** generated by a separate Claude Haiku call that reads the diff. Questions target: (a) what the change does, (b) a detail in the implementation, (c) a side effect or caveat.
  - **Free-response prompt**: "In your own words, explain what this change does and why." Minimum 100 characters.
  - **Actions**: "I understand" (requires ≥2/3 MC correct AND ≥100 chars free-response), "Skip this review", "Hold for later".
- Every gate interaction is recorded in `review_events` with outcome: `passed`, `skipped`, `held`.
- **Spaced re-read**: 7 days after a change is accepted (passed or skipped), a notification appears in the existing Notifications view: "Review your change from last week." Clicking opens the same gate with fresh MC questions regenerated from the diff. Answering correctly reinforces understanding; failing surfaces a "maybe re-read the change?" prompt and extends the review interval.
- A "Comprehension" stats panel (inside the existing Stats plugin) shows: gate trigger rate, pass rate, skip rate, average free-response length, trend lines. This is the sustainability instrument.

## 3. Architectural decisions

1. **Gates are post-hoc, not pre-commit.** Gates fire after the turn completes and Claude's edits are on disk. They gate the Puffin-level "mark this turn complete and move on" transition, not the filesystem operation. This matches how developers actually work (they want to see the change) and avoids interfering with Claude's autonomous flow.
2. **Skip is always available.** Gates never block the user indefinitely. A `Skip` action always works; its cost is a recorded event, nothing more. This is critical: the point is to **measure** whether comprehension is happening, not to coerce it. A gate that blocks is a gate the user will disable.
3. **Questions come from a cheap model.** MC question generation uses `claude-haiku-4-5` with a tight prompt template and `--max-turns 1`. Generation happens in the background as soon as the turn completes, so the modal appears without perceptible latency. Failed generation falls back to a single hand-written prompt ("Describe what this change does.").
4. **Trigger thresholds are configurable per-project.** Default values are opinionated (3 files / 100 lines / migrations / core paths). A project config section lets the user raise thresholds, disable specific triggers, or turn the feature off entirely. Disabling is fully supported — the feature is opt-out, and that is the point. The decision to disable is itself logged once so the user cannot forget they disabled it.
5. **Spaced re-read cadence is fixed at 7 days initially.** Configurable once a baseline exists. After the re-read, a second reinforcement fires at 30 days *if* the 7-day review passed; skipped reviews do not schedule a 30-day follow-up (we do not pester).
6. **No model grading of free-response.** Puffin does not judge whether the free-response is "right." Length alone is the gate: ≥100 characters. The point is to force articulation, not to produce an evaluated answer. This keeps cost near zero and avoids a judgmental dynamic.
7. **Never hides the accept button.** The modal always offers a clear, labeled Skip. The feature must not feel adversarial or paternalistic — it is a prompt for reflection, with measurement attached.

## 4. Data model

### Migration 013: `013_review_events.js`

```sql
CREATE TABLE review_events (
  id                   TEXT PRIMARY KEY,
  branch_id            TEXT,
  prompt_id            TEXT,
  claude_session_id    TEXT,
  trigger_type         TEXT NOT NULL,          -- 'file_count' | 'line_count' | 'migration' | 'core_path'
  trigger_detail       TEXT,                   -- JSON describing what triggered
  diff_summary         TEXT,                   -- JSON: files + line counts
  questions            TEXT,                   -- JSON: [{q, options, correctIdx}]
  answers              TEXT,                   -- JSON: {mc: [...], freeResponse: "..."}
  mc_correct           INTEGER,                -- count of correct MC answers
  free_response_chars  INTEGER,
  outcome              TEXT NOT NULL,          -- 'passed' | 'skipped' | 'held' | 'pending'
  gate_opened_at       TEXT NOT NULL DEFAULT (datetime('now')),
  gate_closed_at       TEXT,
  scheduled_rereview_at TEXT,                  -- for spaced re-read
  parent_review_id     TEXT,                   -- if this is a re-read of an earlier event
  FOREIGN KEY (parent_review_id) REFERENCES review_events(id) ON DELETE SET NULL
);
CREATE INDEX idx_review_events_branch ON review_events(branch_id);
CREATE INDEX idx_review_events_outcome ON review_events(outcome);
CREATE INDEX idx_review_events_rereview ON review_events(scheduled_rereview_at) WHERE scheduled_rereview_at IS NOT NULL;
CREATE INDEX idx_review_events_prompt ON review_events(prompt_id);
```

## 5. Main-process work

### Files created

- `src/main/comprehension/trigger-evaluator.js` — `shouldTriggerGate(completionData, config)` → `{ triggered: bool, reasons: string[] }`. Pure function over the list of modified files and their line counts.
- `src/main/comprehension/question-generator.js` — `generateQuestions(diff, model)` spawns a Haiku call with a prompt template and parses MC output. Timeout 15 seconds; returns fallback on failure.
- `src/main/comprehension/prompt-templates/mc-v1.md` — versioned prompt for generating MC questions.
- `src/main/comprehension/rereview-scheduler.js` — periodic check (runs every 5 minutes in the main process) that queries `review_events WHERE scheduled_rereview_at <= now() AND outcome IN ('passed', 'skipped')` and emits `comprehension:rereviewDue` events.
- `src/main/database/migrations/013_review_events.js`.
- `src/main/database/repositories/review-events-repository.js`.

## 8. Manual verification steps

1. Submit a prompt that modifies 1 file with a small change. Verify no gate fires.
2. Submit a prompt that modifies 4 files. Verify the gate modal opens with diff summary, 3 MC questions, and a free-response field.
3. Answer 2/3 MC correctly. Type 50 characters. Verify the "I understand" button remains disabled.
4. Type 100+ characters. Verify "I understand" becomes enabled. Click it. Verify a `review_events` row is written with outcome `passed`.
5. Submit another multi-file prompt. Click "Skip this review". Verify a row is written with outcome `skipped`.
6. Submit a prompt that creates a file matching `**/migrations/**`. Verify the gate triggers even if only 1 file changed.
7. Open the Comprehension stats panel. Verify metrics render with recent gate events counted.
8. Force-set `scheduled_rereview_at` to now on a past row. Wait up to 5 minutes. Verify a re-review notification appears.
9. Disable the feature in config. Submit a multi-file prompt. Verify no gate fires but the disable event is logged.
10. Measure subjective experience: after 2 weeks of daily use, does the feature feel helpful, annoying, or forgotten? Log in a self-report note attached to the stats panel.

## 9. Open questions

- Threshold calibration: 3 files / 100 lines / 7 days are guesses. After 4 weeks of dogfooding, revisit based on observed skip rate. If skip rate >80%, thresholds are too low. If <20%, they are too high.
- Question quality: if Haiku-generated MC questions are bad often enough that users rightly dismiss them, the feature becomes noise. Plan: an "was this question useful?" inline feedback that writes to `review_events.answers.feedback`, used to iterate on the prompt template.
- Should the gate fire during automated sprint implementation? Default: no for sprint-orchestrated turns (they run unattended overnight); yes for interactive turns. Add a banner in the Evaluation tab (RIS-05) pointing to "X turns in this sprint exceeded comprehension thresholds — review them here."
- Free-response storage: does Puffin preserve the user's written reflections as a learning artifact? Yes — they are kept indefinitely and searchable from the stats panel. This turns the feature into a personal coding journal.
- Privacy: if Puffin ever adds telemetry, comprehension data must never leave the device. State this explicitly in docs and enforce with a linter rule in the telemetry module.
