# Code Review: Database Integrity Review

**Date:** 2026-04-24

## Summary
Inspected all 11 migrations under `src/main/database/migrations/`, the four repository files in `src/main/database/repositories/`, plus all DB-writing call sites in `src/main/puffin-state.js`, `src/main/ipc-handlers.js`, `src/main/metrics-service.js`, and `src/main/cre/`. Foreign key enforcement is ON (`connection.js:64`), which makes `ON DELETE CASCADE` gaps load-bearing. The most serious finding is a repeat of a previously-fixed class of bug: `puffin-state.js` resets `user_stories` directly without purging the dependent `completion_summaries`, which will fail under FK enforcement. Three FK declarations (`completion_summaries.story_id`, `cre_ris.plan_id`, `cre_inspection_assertions.plan_id`) omit CASCADE and carry no comment, and several multi-step write sequences (JSON migration of active sprint, DB reset, assertion sync) are not wrapped in a transaction. Repository writes done outside repository boundaries (direct `db.prepare(...)` in CRE and IPC handlers) consistently skip cache/state refresh. One repository (`completion-summary-repository.js`) also accepts caller-supplied IDs into a UNIQUE `PRIMARY KEY` column.

## Findings

- **[CRITICAL]** MISSING_DEPENDENT_DELETE src/main/puffin-state.js:3996 — `DELETE FROM user_stories` in `resetDatabase()` runs with no prior `DELETE FROM completion_summaries`. FKs are enforced (`connection.js:64`) and `completion_summaries.story_id → user_stories(id)` lacks `ON DELETE CASCADE` (migration 009:34), so this will throw `FOREIGN KEY constraint failed` whenever any completion summary exists. Same root cause as the archive/delete bug already fixed in `user-story-repository.js:503,575`.
- **[CRITICAL]** MISSING_CASCADE src/main/database/migrations/009_add_completion_summary.js:34 — `FOREIGN KEY (story_id) REFERENCES user_stories(id)` has neither `ON DELETE CASCADE` nor a cleanup comment. Repositories must remember to delete `completion_summaries` first on every story removal path; already caused production bugs and will recur at new call sites.
- **[IMPORTANT]** MISSING_CASCADE src/main/database/migrations/007_cre_tables.js:42 — `cre_ris.plan_id → cre_plans(id)` has no `ON DELETE CASCADE` / `RESTRICT` and no cleanup comment. Deleting a plan leaves orphan RIS rows (or fails with FK enforcement). Rename migration 008 preserves the same FK without adding CASCADE.
- **[IMPORTANT]** MISSING_CASCADE src/main/database/migrations/007_cre_tables.js:62 — `cre_inspection_assertions.plan_id → cre_plans(id)` has no `ON DELETE CASCADE` / `RESTRICT` and no cleanup comment. Same orphan/constraint-failure risk as the RIS case.
- **[IMPORTANT]** UNTRANSACTED_WRITE src/main/database/json-migrator.js:323 — `_migrateActiveSprint()` runs `INSERT INTO sprints` followed by a loop of `INSERT INTO sprint_stories` and a `_recordMigration(...)` write with no `db.transaction(...)` wrapper. A mid-loop failure leaves a partially migrated sprint with only some junction rows.
- **[IMPORTANT]** UNTRANSACTED_WRITE src/main/puffin-state.js:3996 — `resetDatabase()` executes `DELETE FROM user_stories` and `DELETE FROM archived_stories` as separate statements without a transaction. If the first succeeds and the second fails, state is inconsistent.
- **[IMPORTANT]** UNTRANSACTED_WRITE src/main/ipc-handlers.js:693 — `syncAssertionsFromCreTable` reads from `inspection_assertions` and writes to `user_stories` in a per-story loop with no `db.transaction(...)`. Partial sync is possible on mid-loop error, leaving some stories in sync and others stale.
- **[IMPORTANT]** CALLER_SUPPLIED_ID_REUSE src/main/database/repositories/completion-summary-repository.js:47 — `_summaryToRow()` uses `id: summary.id || crypto.randomUUID()`. Since `completion_summaries.id` is `PRIMARY KEY` (UNIQUE), any caller passing an `id` risks UNIQUE-constraint collisions identical to the root-cause bug documented for `_validateAssertion` in memory. Always call `crypto.randomUUID()`; ignore caller-supplied IDs.
- **[IMPORTANT]** NO_REFRESH_AFTER_WRITE src/main/cre/index.js:412 — `cre:generate-assertions` writes `UPDATE user_stories SET inspection_assertions = ?` directly via `ctx.db.prepare(...)` and returns without reloading `puffinState.userStories` or dispatching a refresh. In-memory model remains stale until the next full reload; reproduces the class of bug already documented in the "Sprint stories not synced with DB assertions" gotcha.
- **[IMPORTANT]** NO_REFRESH_AFTER_WRITE src/main/ipc-handlers.js:715 — `syncAssertionsFromCreTable` updates `user_stories.inspection_assertions` but returns only `{ success, synced }`. It does not call `puffinState.loadUserStories()` or emit a state refresh, so renderers working from the cached `puffinState.userStories` will still see empty assertions until another path reloads.
- **[IMPORTANT]** NO_REFRESH_AFTER_WRITE src/main/puffin-state.js:687 — `getStoryInspectionAssertions()` writes `UPDATE user_stories SET inspection_assertions = ...` as a side-effect sync but does not invalidate `this.userStories` / `this.invalidateCache()`. Subsequent reads served from the cache return the pre-sync empty value.
- **[INFO]** CALLER_SUPPLIED_ID_REUSE src/main/database/repositories/user-story-repository.js:112 — `create()` inserts `row.id` from the caller into `user_stories.id` (PRIMARY KEY). Acceptable where IDs come from JSON migration, but there is no UNIQUE-collision guard; AI-derived stories should generate `crypto.randomUUID()` at the boundary or the repository should fallback to `randomUUID()` when `story.id` is falsy.
- **[INFO]** CALLER_SUPPLIED_ID_REUSE src/main/database/repositories/sprint-repository.js:164 — `create()` inserts `row.id` from the caller into `sprints.id` (PRIMARY KEY). Same caveat as above; tighten by generating the UUID inside the repository when the caller omits it.
