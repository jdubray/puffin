# Code Review: IPC Communication Review

**Date:** 2026-04-24

## Summary
Audited ~200 IPC handler registrations across `src/main/main.js`, `src/main/ipc-handlers.js`, `src/main/cre/index.js`, and `src/main/plugins/plugin-context.js`, plus the renderer `invoke()` call sites. The channel layer is well-structured overall — fire-and-forget flows (`claude:submit`, `claude:cancel`, `vibe:submit`, `claude:deriveStories`) correctly use `ipcMain.on()`, and the dominant `{ success: Boolean, ... }` response contract is consistently honored by ~90% of handlers. The main issues are a small cluster of "legacy" handlers that return bare values (boolean / raw object / `null`) and therefore break the contract callers assume, an inconsistent channel-name convention (camelCase vs. kebab-case action segments), and plugin-related `ipcMain.handle()` registrations that run after the `BrowserWindow` has been constructed. Renderer call sites that touch `result.data` / `result.error` all guard on `result.success` first — no violations found there.

## Findings

- **[CRITICAL]** HANDLER_NO_SUCCESS_FIELD src/main/main.js:323 — `app:getInitialState` returns `{ projectPath, recentProjects, openPluginsManager }` with no `success` field, so any caller using `result.success` to detect failure silently treats this as a falsy result.
- **[CRITICAL]** HANDLER_NO_SUCCESS_FIELD src/main/main.js:554 — `app:getRecentProjects` returns a raw array (`return getRecentProjects()`) instead of `{ success: true, projects }`; callers cannot distinguish "empty list" from "IPC error".
- **[CRITICAL]** HANDLER_NO_SUCCESS_FIELD src/main/ipc-handlers.js:281 — `tools:checkSnip` returns `{ installed, path }` / `{ installed: false }` without a `success` field.
- **[CRITICAL]** HANDLER_NO_SUCCESS_FIELD src/main/ipc-handlers.js:1558 — `claude:check` returns `{ available, version }` without a `success` field; on error it still returns `{ available: false, version: null }` with no `error` surfaced to the renderer.
- **[CRITICAL]** HANDLER_NO_SUCCESS_FIELD src/main/ipc-handlers.js:1570 — `claude:isRunning` returns a bare `Boolean` (also `false` on error, collapsing two distinct states).
- **[CRITICAL]** HANDLER_NO_SUCCESS_FIELD src/main/ipc-handlers.js:1910 — `claude:getModels` returns `{ models, default }` with no `success` field; the renderer destructures these at `src/renderer/app.js:887` and would `TypeError` on the error path.
- **[CRITICAL]** HANDLER_NO_SUCCESS_FIELD src/main/ipc-handlers.js:1945 — `vibe:check` returns `{ available }` / `{ available: false, error }` — no `success` wrapper.
- **[CRITICAL]** HANDLER_NO_SUCCESS_FIELD src/main/ipc-handlers.js:1955 — `vibe:isRunning` returns a bare `Boolean`.
- **[CRITICAL]** HANDLER_NO_SUCCESS_FIELD src/main/ipc-handlers.js:2012 — `vibe:getModels` returns `{ models, default }` without a `success` field.
- **[CRITICAL]** HANDLER_NO_SUCCESS_FIELD src/main/ipc-handlers.js:3502 — `plan:readLatest` returns either `null` or `{ filename, filePath, content }`; neither shape carries `success`, forcing callers to do `if (planFile)` null-checking instead of the documented contract.
- **[IMPORTANT]** HANDLER_REGISTERED_AFTER_WINDOW src/main/main.js:456 — `setupPluginHandlers(ipcMain, pluginLoader)` is invoked from `initializeProject()`, which runs after `createWindow()` / `new BrowserWindow(...)` (main.js:284, 610). Registering `ipcMain.handle()` post-window creation is the exact race pattern the fix in `MEMORY.md` warned against ("IPC handler registration timing"). Renderer code that fires these channels before project init will get "no handler registered".
- **[IMPORTANT]** HANDLER_REGISTERED_AFTER_WINDOW src/main/main.js:492 — `setupPluginManagerHandlers(ipcMain, pluginManager, mainWindow)` likewise registers `plugins:enable`, `plugins:disable`, `plugins:getInfo`, etc., after the window is constructed.
- **[IMPORTANT]** HANDLER_REGISTERED_AFTER_WINDOW src/main/main.js:493 — `setupViewRegistryHandlers(ipcMain, ...)` registers the `plugin:register-view`, `plugin:get-sidebar-views`, and ten related channels after the BrowserWindow already exists and the renderer may already be mounting.
- **[IMPORTANT]** HANDLER_REGISTERED_AFTER_WINDOW src/main/main.js:494 — `setupPluginStyleHandlers(ipcMain, pluginManager)` registers `plugin:get-renderer-config`, `plugin:get-style-paths`, `plugin:get-all-style-paths` post-window. The renderer's `plugin-component-loader.js` invokes these at startup.
- **[IMPORTANT]** HANDLER_REGISTERED_AFTER_WINDOW src/main/plugins/plugin-context.js:160 — `ipcMain.handle(qualifiedChannel, ...)` runs during plugin activation, which is triggered from `initializeProject()` well after the BrowserWindow is built. Plugin-contributed channels are therefore visible to the renderer only after a nondeterministic delay.
- **[IMPORTANT]** CHANNEL_NAMING_PATTERN src/main/cre/index.js:213 — `cre:generate-plan` (and siblings `cre:submit-answers` at :252, `cre:refine-plan` at :278, `cre:approve-plan` at :303, `cre:generate-ris` at :324, `cre:generate-assertions` at :350, `cre:verify-assertions` at :431, `cre:update-model` at :457, `cre:refresh-model` at :553, `cre:query-model` at :628, `cre:get-plan` at :646, `cre:get-ris` at :668, `cre:list-ris-story-ids` at :700) all use kebab-case action segments, which conflicts with the camelCase `namespace:actionName` convention used by the majority of channels (`state:updateConfig`, `claude:sendPrompt`, `git:createBranch`, etc.).
- **[IMPORTANT]** CHANNEL_NAMING_PATTERN src/main/ipc-handlers.js:3033 — `plugin:register-view` (and the cluster `plugin:unregister-view` at :3050, `plugin:unregister-plugin-views` at :3061, `plugin:get-sidebar-views` at :3072, `plugin:get-views-by-location` at :3083, `plugin:get-all-views` at :3094, `plugin:get-plugin-views` at :3105, `plugin:get-view` at :3116, `plugin:get-view-summary` at :3130, `plugin:get-renderer-config` at :3162, `plugin:get-style-paths` at :3199, `plugin:get-all-style-paths` at :3226) use kebab-case action segments, diverging from the camelCase convention used by the sibling `plugins:*` namespace (`plugins:list`, `plugins:getInfo`, etc.).
- **[IMPORTANT]** CHANNEL_NAMING_PATTERN src/main/ipc-handlers.js:1401 — `toast-history:getAll` (and `toast-history:add` at :1412, `toast-history:delete` at :1423, `toast-history:deleteBefore` at :1434, `toast-history:clear` at :1445) use a kebab-case *namespace* segment; every other namespace in the project is a single camelCase/lowercase word. This subtly breaks the assumed `namespace:actionName` split pattern (splitting on the first `:` still works, but grep/tooling that assumes `[a-z]+:` will miss these).
- **[IMPORTANT]** CHANNEL_NAMING_PATTERN src/main/plugins/plugin-context.js:154 — `plugin:${this.pluginName}:${channel}` produces three-segment channel names (e.g., `plugin:claude-config:getConfigWithContext`), which does not match the documented two-segment `namespace:actionName` pattern. This is a genuine architectural pattern but is undocumented and breaks simple channel validators.
- **[INFO]** HANDLER_NO_SUCCESS_FIELD src/main/ipc-handlers.js:3601 — `webserver:status` returns `{ success: true, running, port, url }` on the happy path but its return shape is still consumed by callers as if `running` is top-level; low-confidence because `success` IS present, noted only because the adjacent `webserver:siteMap` at :3616 uses the same pattern and both differ from `webserver:start` / `:stop` in how they expose payload data.
