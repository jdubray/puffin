# Code Review: SAM State Management Review

**Date:** 2026-04-24

## Summary
Audited SAM pattern compliance across `src/renderer/sam/`, `src/renderer/lib/state-persistence.js`, `src/renderer/app.js`, `src/main/ipc-handlers.js`, `src/main/claude-service.js`, `src/main/cre/`, and the SQLite repositories. No direct mutations of `this.state.*` were found in renderer handlers — every assertion/story update path dispatches a SAM intent. The `persistActions` whitelist (state-persistence.js:111–141) is in sync with its handler condition blocks in both directions. Two real pending-flag-leak bugs were found: `crePlanningErrorAcceptor` omits `_pendingCreApproval` from its cleanup set (produces an approval-retry loop when approval fails), and the `START_SPRINT_STORY_IMPLEMENTATION` persistence path leaves `_pendingStoryImplementation` set when `claude.submit()` rejects. A third latent bug in `cre-orchestrator.js` sets `_running = true` before `acquireLock()`, so a lock-acquisition throw strands the orchestrator flag as `true`. Most `setTimeout` callbacks that dispatch SAM intents self-validate orchestration status before acting; no unsafe timer dispatches were identified. The `_validateAssertion` AI-generated-ID collision bug documented in memory is already fixed (always uses `uuidv4()`); remaining INSERT callers use UUIDs or renderer-generated timestamp+random IDs where collisions are negligible.

## Findings

- **[CRITICAL]** PENDING_FLAG_NOT_CLEARED_ON_ERROR src/renderer/sam/model.js:2114 — `crePlanningErrorAcceptor` clears `_pendingCrePlanning`, `_pendingCreIteration`, and `_pendingCreAnswers` but omits `_pendingCreApproval`. The success sibling `crePlanningCompleteAcceptor` at line 2103 clears all four. When `handleCreApproval` (app.js:6212) throws and dispatches `crePlanningError` (app.js:6349), `_pendingCreApproval` stays set in the model; the next render cycle sees `state._pendingCreApproval` truthy and re-invokes `handleCreApproval`, producing an approval-retry loop that can only be broken by the `_handlingCreApproval` in-flight guard. Confidence: 92.
- **[CRITICAL]** PENDING_FLAG_NOT_CLEARED_ON_ERROR src/renderer/lib/state-persistence.js:699 — `await window.puffin.claude.submit({...})` inside the `START_SPRINT_STORY_IMPLEMENTATION` branch can reject (CLI spawn failure, or claude-service.js:279–282 "already running" guard). On rejection, `this.intents.clearPendingStoryImplementation()` at line 712 is skipped; the outer `catch` at line 777 only logs. `_pendingStoryImplementation` remains set in the model, so subsequent orchestration ticks never re-queue. Wrap the submit in try/finally or move the clear into a finally block. Confidence: 87.
- **[IMPORTANT]** UNTRACKED_PENDING_FLAG src/main/cre/lib/cre-orchestrator.js:95 — `_running = true` is set at line 95 before `acquireLock()` at line 100; the `try { … } finally { releaseLock(); _running = false; }` only begins at line 102. If `acquireLock()` throws (claude-service.js:211 throws "Claude CLI process is busy" after retry exhaustion), `_running` is left `true` permanently and every subsequent call hits the guard at line 89 ("Orchestrator is already running"). The same pattern recurs in `runApprovalPhase` (line 167 → 171) and `runRefinement` (line 228 → 232). Move `_running = true` inside the try block, or wrap the entire function body with try/finally. Confidence: 83.
- **[INFO]** CALLER_SUPPLIED_ID_IN_INSERT src/main/database/repositories/completion-summary-repository.js:47 — `_summaryToRow` uses `summary.id || crypto.randomUUID()`, preserving caller-supplied IDs when present. `completion_summaries.id` is the PRIMARY KEY, so a non-unique caller-supplied id would fail the INSERT and cascade a failed story completion. Current call sites (ipc-handlers.js:853 `state:storeCompletionSummary`) never pass `id`, so the random-UUID fallback is used and the risk is latent. Prefer unconditionally generating a fresh UUID (mirroring the `_validateAssertion` fix that resolved the IA001 collision). Confidence: 80.
- **[INFO]** CALLER_SUPPLIED_ID_IN_INSERT src/main/claude-service.js:2510 — The `generateInspectionAssertions` system prompt still instructs the model to emit sequential IDs ("format: IA + 3 digits") — the exact pattern that caused the historical `_validateAssertion` collision bug. This path currently writes to `user_stories.inspection_assertions` (a JSON column with no UNIQUE constraint), so the collision is latent rather than active. It is a regression risk if a future change routes these assertions through the `inspection_assertions` table. Confidence: 80.
