The spine

Work moves in one direction. Every station has an owner and an exit condition, and the exit is decided by a gate — a mechanical check — not by a judgement call. Where a gate isn't wired yet, the station says so rather than pretending.

GATE · polyvers on change

Two lanes, chosen by the component

ComponentBuilt byProved by
Holds state, in JS/TS polygen — contract → module → invariants → corpus Model check over every reachable state, then the acceptance verifier
Holds state, other language Authored by the session under capture-ready — polygen emits JavaScript only Trace-corpus validation and replay, then the acceptance verifier
Everything else Authored by the session from the prompt spec The acceptance spec's verifier command — deliverables and checkable criteria

The difference is worth stating plainly: a model check is a proof over all reachable states, an acceptance verifier is a set of examples. Tests sample; the checker exhausts. So the stronger lane is used wherever it is available — and where it isn't, the spec says so rather than implying the weaker one is equivalent.

The middle row is the one people get wrong, including this sheet in its first revision. The checker derives its transition relation mechanically from a SAM v2 JavaScript module, so it cannot explore a Python or Go one — losing polygen there costs the exhaustive proof, not just the head start. What crosses the language boundary is the corpus: the capture-ready skill shapes the module so one step listener emits {pre, action, data, post} windows, and those windows feed corpus validation, replay and polyvers' stimuli gate unchanged. The module stays in its language; only the evidence travels.

Two backward bends, one budget, and every bend carries evidence. A failed validation or a review finding returns the card to implement with the concrete signal that caused it — missing-deliverable, verifier-failed, defect, spec-mismatch — never a bare “try again”. They share one budget of two; the third correction, from either source, sends the card to needsHuman with budget-exhausted. There is no re-plan action. Planning is entered once per attempt, and the only road back to it is a human taking RESUME — deliberately, with a fresh budget.

03

Who owns what

Seven engines, each with one job. Everything below runs locally and without an API key except the sessions themselves — generation is always client-side, which is why the design store never holds a key.

EngineOwnsProduces
GLM The sekkei — nodes, strata, edges, change requests, drift The verifier's verdict (DoRC), the SCR status FSM
polygen Authoring new stateful code from a contract — JavaScript/TypeScript only SAM v2 module + invariants + trace corpus, self-repaired
polygraph Verification — replay and model check, whatever wrote the machine Counterexamples, reachable-state coverage
polynv Invariant elicitation against the real state graph An append-only intent-ledger of confirmed constraints
polyvers Version change — is this safe against the fleet? A compatibility verdict and a migration scaffold
polyrun Durable execution — every card is an instance The board's state and its journal
polyviz Figures Deterministic SVG, no model call at render time

Where invariants come from

polynv mines candidates by enumerating the machine's state graph, so it cannot elicit from a spec that has no code behind it. Invariants are not a pre-code step. The order is: spec → contract → polygen (draft invariants) → polynv (confirm them). What lands back on the spec is a reference to the ledger record — id, what it constrains, who confirmed it, when — never a copy of the predicate. The predicate has one home, so there is nothing to diverge.

05

Starting a project

The order the pipeline expects on a sekkei that is authored but has no code behind it yet — where the integration gate is red for the one honest reason, and everything else is green.

  1. Scaffold, and turn gate 7 green

    One card that creates package.json, tsconfig.json and installs the compiler at source_dir. Not a component — it exists so every later card validates against a real project.

  2. One component at a time

    DoRC gate decides ready. The prompt spec briefs the session. A state machine in JS/TS goes to polygen and arrives verified; one in another language is authored and then model-checked all the same; everything else is proved by its acceptance verifier. Elicit invariants where there is a machine, link them to the spec, then let the verifier decide done.

  3. Change becomes a version question

    Once code exists, a spec change is an SCR, and the SCR is gated by polyvers: compatibility lanes, replay against fleet snapshots, and a migration scaffold when the shape moved. Drift stops being invisible.

Two decisions this shape assumes

  • Puffin owns the card, not the pipeline. When a card starts work it should invoke GLM's /glm-build — generate, verify, attest — rather than reimplementing that orchestration on the Puffin side.
  • Doneness is mechanical or it is disclosed. Where no gate is wired, the card carries an ungated mark instead of a green tick. A verdict nobody computed is worse than an admitted gap.
